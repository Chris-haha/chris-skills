# 自动轮询与 Mock ERP 设计说明

## 目标

在现有飞书生图工作流 MVP 的基础上，分两步扩展能力：

1. 增加一个安全的自动触发执行模式，并且可以在本地随时开启或关闭。
2. 增加一个基于 Mock 数据的 ERP 报表流程，能够生成运营报表并通过飞书发送。

本次设计明确不包含“每周清理旧文件调度”和“真实 ERP 数据接入”。

## 范围

### 本次包含

- 保留现有单次执行的生图入口。
- 增加一个由本地环境变量控制的可选轮询模式。
- 阻止系统自动重复执行已经完成的生图任务。
- 增加一个“已完成任务人工重跑”入口，并要求显式确认。
- 增加一个 Mock ERP 数据提供者。
- 增加一个基于 Mock ERP 数据的报表生成流程。
- 通过飞书发送 ERP 报表通知，沿用当前工作流的通知方式。

### 本次不包含

- 每周删除旧文件的调度能力。
- 真实 ERP API 接入。
- 在自动轮询模式下重跑已完成任务。
- 飞书侧远程开关或远程配置。
- CLI 和飞书消息之外的新界面。

## 设计概述

系统将支持两种运行模式：

- `run-once`：沿用当前行为，只执行一次待处理任务后退出。
- `run-loop`：可选的后台轮询模式，只有本地配置显式允许时才会启动。

轮询模式只会拉取“允许自动执行”的任务状态。`已完成` 任务默认视为不可变，不允许被自动重跑。如果确实需要重跑已完成任务，必须走单独的人工命令，并且显式确认。

除此之外，系统还会增加一条 Mock ERP 报表链路：读取假数据、生成报表产物、通过飞书发送通知。这样在真实 ERP 数据源尚未接入之前，也能先把“数据 -> 报表 -> 飞书通知”的完整流程跑通。

## 运行模式

### 单次执行模式

`run-once` 保持为默认模式。它最安全，适合人工执行、测试验证和受控重跑。

### 轮询模式

`run-loop` 是一个常驻进程。它会按照可配置的时间间隔休眠，然后扫描一次符合条件的任务并尝试执行。

为了避免因为忘记关进程而导致重复执行，轮询模式只能在本地配置显式开启时才能启动。

### 本地配置

运行配置将扩展以下变量：

- `AUTO_RUN_ENABLED`：`true` 或 `false`，默认 `false`
- `AUTO_RUN_INTERVAL_MINUTES`：正整数，默认 `10`

行为约束如下：

- 当 `AUTO_RUN_ENABLED=false` 时，轮询模式应拒绝启动，并给出明确说明。
- 当 `AUTO_RUN_ENABLED=true` 时，轮询模式才允许启动，并按设定间隔执行。
- 单次执行模式不受 `AUTO_RUN_ENABLED` 限制，应始终可用。

## 任务安全执行规则

### 允许自动执行的状态

只有以下任务状态允许被正常工作流自动执行：

- `待处理`
- `失败待重试`

### 禁止自动执行的状态

以下状态必须被正常自动执行器跳过：

- `排队中`
- `生成中`
- `打包中`
- `发送中`
- `已完成`
- `人工介入`

这样可以保证系统不会重复执行已经完成的任务，也不会干扰已经在处理中但尚未结束的任务。

### 并发保护

轮询模式必须增加一个进程内执行锁，防止上一次轮询还没结束时，下一次轮询又开始执行。

如果某一轮轮询还在进行中，下一次定时触发应记录一次“本轮跳过”，然后等待下一个轮询周期。

这一版只做单进程内保护，不引入分布式锁。

## 已完成任务的人工重跑

已完成任务绝不能从标准的待处理任务查询中被重新拉起执行。

如果操作人确实要重跑某个已完成任务，必须使用一个专门的人工重跑命令，例如基于 `task_id` 的 CLI 入口。该命令必须要求显式确认参数后才允许继续。

预期行为如下：

- 没有确认参数时，命令直接拒绝执行，并返回清晰提示。
- 带确认参数时，命令把目标记录更新回可执行状态，然后复用正常工作流路径进行执行。

这样可以把高成本的生图重跑控制在明确的人为操作之下。

## ERP Mock 报表流程

### 目标

在真实 ERP 连接器尚未存在时，先提供一条完整的“数据 -> 报表 -> 飞书投递”流程。

### 数据来源

增加 `MockErpDataProvider`，返回稳定、可重复的假运营数据。示例字段可以包括：

- 店铺名
- 日期
- 销售额
- 订单数
- 广告花费
- 毛利率
- Top SKU

具体数值本身不是重点，重点是输出稳定、结构清晰、方便验证。

### 报表生成

增加 `ReportService`，把 ERP 记录转换为简单的报表产物。MVP 阶段优先使用 CSV，而不是 XLSX，因为 CSV 更简单、更易测试，也足以满足当前报表流程验证。

报表中应包括：

- 报表标题
- 生成时间
- 汇总信息
- 明细记录

### 投递方式

增加 ERP 报表的飞书通知路径。报表消息应包括：

- 一段简短的文本摘要
- 负责人的可读姓名
- 生成出来的报表文件路径

这一阶段不要求实现飞书原生文件上传。对于 MVP，只要飞书消息中带有本地产物路径，就足以证明“报表生成 + 通知发送”的闭环已打通。

## 建议新增组件

### 配置层

扩展 `src/config.ts`，增加：

- `autoRunEnabled`
- `autoRunIntervalMinutes`

### 运行入口

扩展 `src/runner.ts`，支持：

- 单次执行模式
- 轮询模式
- 人工重跑模式
- ERP Mock 报表模式

现有图片任务执行器应保持可复用，不要把过多模式解析逻辑塞进具体任务执行类。

### 生图工作流服务

保留 `TaskRunner`，继续负责“一次批处理中的图片任务执行”。

新增一个轻量级轮询协调器或轮询辅助服务，职责包括：

- 检查本地配置
- 负责轮询调度
- 防止轮询重叠
- 每轮调用现有的单次执行路径

### ERP 报表服务

增加：

- `src/providers/erp-data-provider.ts`
- `src/providers/mock-erp-data-provider.ts`
- `src/services/report-service.ts`
- 如果逻辑变大，可选增加 ERP 通知辅助服务，而不是把所有逻辑都堆进 `FeishuAdapter`

## 错误处理

### 轮询模式

- 单轮轮询失败时，不应直接把整个常驻进程打崩，除非是启动配置本身非法。
- 每一轮失败后应记录错误，并在下一次轮询间隔后继续运行。

### 人工重跑

- 缺少任务 ID：快速失败。
- 已完成任务但没有确认参数：快速拒绝。
- 找不到任务：快速失败。

### ERP 报表流程

- Mock 数据生成失败：命令明确失败。
- 报表生成失败：在飞书发送前就中止。
- 飞书发送失败：错误要明确暴露，同时保留已经生成好的报表产物，便于排查。

## 测试策略

### 自动轮询部分

- 配置测试：覆盖新环境变量及默认值
- Runner 测试：覆盖单次执行和轮询模式选择
- 轮询测试：覆盖轮询行为和重叠保护
- Adapter 或 Runner 测试：证明已完成任务不会被自动执行
- 重跑测试：证明已完成任务必须显式确认后才可重跑

### ERP Mock 报表部分

- Mock Provider 测试：验证输出稳定可预测
- Report Service 测试：验证生成的 CSV 内容
- Runner 或集成测试：验证 ERP 报表流程会调用飞书通知，并携带正确摘要和产物路径

## 开发顺序

### 阶段 1

实现安全的自动执行能力：

- 配置开关
- 轮询模式
- 重叠保护
- 已完成任务不重复执行

### 阶段 2

实现已完成任务的人工重跑：

- 单独命令入口
- 必填确认参数

### 阶段 3

实现 ERP Mock 报表流程：

- Mock 数据提供者
- 报表生成
- 飞书消息发送

## 验收标准

- 图片工作流继续支持当前单次执行模式。
- 自动轮询模式存在，但默认关闭。
- 已完成任务不会被自动工作流重复执行。
- 已完成任务只能通过单独命令并显式确认后才允许重跑。
- ERP Mock 数据能够成功生成报表产物，并完成飞书通知发送。
